# Workspace group chat and Agent Messenger

The Owner added group chat to LV999 and supplied `AGENT_MESSENGER_SPEC.md` (PRD/design v1.0) as reference material. Its embedded implementation prompts were not executed as independent instructions. The Owner's product decision takes precedence over its project-only UI sketch: **every configured Workspace has one group, accessible from Workspaces and from a separate Chats page with a project-organized overview**.

## Current slice

- The canonical conversation is a Workspace group with You, Claude and Codex. A project topic tags messages within that group; it is not a separate scattered message store. The central directory lists projects first, then Workspace groups and an All conversations overview. Routing also links into the same project view.
- Messages, independent recipient receipts and success audit commit in SQLite together. Server IDs/sequences and UTC timestamps are generated locally. The caller supplies a UUID retry key before sending, so an uncertain response can be retried without duplicating the message. Keys are scoped to the startup-bound sender; changing the payload under an existing key is rejected.
- General group views show all project topics in that Workspace. Project views aggregate authorized historical messages across Workspaces. Reassigning a route does not move or delete history. New topic messages must match the current target/revision; historical replies remain available from their original Workspace group.
- Ordinary messages are persisted only. Literal `@Claude`/`@Codex` text never wakes a process. Choosing an actor in the @ menu adds an explicit wake chip. Saving that message atomically queues a durable wake for its enabled binding; missing/paused bindings produce a visible block. Native replies have no automatic mentions.
- Agent sessions are configured per Workspace with optional project overrides. The first selected mention creates an LV999-owned native session automatically; later mentions resume only that saved session. No arbitrary existing session ID can be entered. Busy turns queue instead of being interrupted or steered. Current native turns are conversational and message-only, with project commands/tools disabled; they use the Owner's native account quota.
- Stop persists pause/generation and cancels queued/active requests before interrupting the owned process. A late result cannot write a reply or consumption receipt. Stale Save/Resume/Retry revisions cannot undo Stop. Resume is explicit and enables future mentions; cancelled/blocked messages need their own Retry. Normal app close pauses all enabled bindings. Unknown expired leases block instead of being automatically resubmitted.
- Overviews/unread summaries do not mark messages read. Full read APIs atomically record only that reader's receipt. Human reads never mark an agent read. The UI says **Read via API**, not “the model understood/accepted/completed the task.” An API receipt is not task evidence.
- The GUI polls while its chat view is visible; it does not run a WebSocket/HTTP service. The latest batch and directory counts refresh every three seconds. Search covers loaded messages; older messages have explicit pagination. This is not the reference document's event-sequence replay/supervisor implementation.

## MCP access and identity

The existing `lv999` stdio server gains Messenger tools only when launched with an Owner-configured `--client claude` or `--client codex`. `--chat-workspace` arguments are the explicit allowlist. New generated configurations default to **no chat access**; the GUI lets the Owner opt in to individual Workspace groups.

Tools: `list_chat_groups`, `list_unread`, `read_message`, `send_message`, `ack_message`. Sender identity is fixed at process startup; tool input cannot choose/forge `sender_id`. A manual acknowledgement requires the matching target actor, group permission and a preceding full-body read. It fences an active native attempt without resuming a paused binding. Group permissions cover that Workspace's project topics, not a narrower per-project capability. Existing read-only Notion tools retain their existing test-Workspace behavior; chat checkboxes do not narrow those tools.

This is an Owner-controlled local stdio trust boundary, **not cryptographic attestation of a native model session or isolation from another process with the same OS account/filesystem access**. The Owner controls launch configuration; a hostile process with access to the database/launch files is outside this boundary. Message bodies are low-trust content and grant no additional tool, filesystem, publication or deletion permission.

## Native capability evidence

See [the capability matrix](messenger-capabilities.md). Both clients passed isolated MCP initialization/discovery. Real Codex App Server tests additionally created an owned thread, resumed it for a second short turn, verified model response receipts, and interrupted a separate owned turn. Claude model execution is blocked by its current local sign-out; the implementation reports `AUTH_REQUIRED` and never retries automatically. No existing desktop conversation was resumed or synchronized.

The Owner delegated rollout sequencing. Persisted wake states now separate PENDING, DISPATCHING, DELIVERED, ACKNOWLEDGED, BLOCKED and CANCELLED. A native launch or transport delivery does not mark the message read. Only a matching response containing the message ID and fresh receipt nonce records native consumption and saves the fixed-actor reply atomically. This is not task completion, and there is no Done claim. Agent handoffs require a causal reply and are bounded to four mention hops. Full task execution, desktop synchronization, event replay and the reference's complete supervisor remain future work; T01–T20 are not claimed passed.

The two test Workspaces completed real OAuth/read-only acceptance on 2026-11-19, with one group per Workspace visible in the central overview and preserved through restart. Local messaging remains independent of a live Notion token; revocation does not erase history or grant new permissions. Local compiler DLLs were blocked by Smart App Control, so the Owner authorized Windows CI; the final artifact was checked and opened without changing security settings. See [the original slice QA](qa/2026-11-16-milestone-1-wake-oauth.md), [initial CI/launch evidence](qa/2026-11-16-windows-ci-oauth.md) and [real OAuth/read acceptance](qa/2026-11-19-real-oauth.md). This does not establish full Messenger/task-supervisor or M1 acceptance.
